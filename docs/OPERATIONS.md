# pm-edge Operations Runbook

This document describes how the Phase 1 forward data layer is operated. It covers the VPS producer, the static status page, the laptop rsync/archive flow, and the notebook analysis workflow.

## Concept of Operation

The forward data layer has two roles:

1. **VPS producer:** runs the forward indexer continuously under systemd. It discovers active Polymarket and Kalshi markets, filters to a liquidity-focused universe, maintains book state, and writes partitioned parquet under `/opt/pm-edge/data/raw/forward_index/`.
2. **Laptop consumer:** periodically pulls completed parquet files from the VPS with rsync. DuckDB reads the local parquet archive directly for notebooks and analysis.

The VPS does not run strategy research notebooks. The laptop does not collect live venue data. This split keeps the always-on capture process simple and keeps exploratory work off the production box.

```text
Public venue APIs
  Polymarket Gamma + CLOB WS
  Kalshi REST
        |
        v
DigitalOcean VPS
  systemd forward-indexer
  /opt/pm-edge/data/raw/forward_index/*.parquet
  /opt/pm-edge/data/ops_status.html
        |
        | rsync
        v
Laptop
  $PM_EDGE_LOCAL_FORWARD_INDEX_DIR
  DuckDB + notebooks/
```

Real-money execution is not part of this operating model. The system is in paper/research mode until enough forward book data exists and a separate execution simulator validates fill assumptions.

## VPS Forward Indexer

The deployed service runs as:

```bash
sudo systemctl status forward-indexer.service
journalctl -u forward-indexer.service -f
```

Default data location:

```text
/opt/pm-edge/data/raw/forward_index/
```

Expected table layout:

```text
order_book_snapshots/venue=<venue>/date=<YYYY-MM-DD>/*.parquet
trade_events/venue=<venue>/date=<YYYY-MM-DD>/*.parquet
market_metadata_snapshots/venue=<venue>/date=<YYYY-MM-DD>/*.parquet
```

Normal heartbeat logs include:

- `markets_tracked`
- `snapshots_per_second`
- `websocket_connections`
- `errors_since_last_heartbeat`
- `dedupe_keys_retained`
- `memory_mb`

Operationally, watch for:

- No heartbeat for more than a few minutes.
- Repeated `polymarket_gamma_retry` events.
- Repeated WebSocket reconnects.
- Memory above the configured cap.
- Snapshot counts dropping sharply for either venue.

## Static VPS Status Page

The status page is generated by:

```bash
/opt/pm-edge/.venv/bin/python /opt/pm-edge/scripts/ops_status.py
```

Default output:

```text
/opt/pm-edge/data/ops_status.html
```

The page contains:

- systemd service status, PID, restarts, and memory
- latest heartbeat and rolling snapshot rate
- snapshot/trade capture counts by venue
- storage usage and projected disk runway
- Kalshi book-quality checks
- Polymarket WebSocket-vs-REST source breakdown
- recent gap detection
- recent journal errors and reconnect counts

Install the cron entry manually from `deploy/forward_indexer/ops_status.cron`. The intended schedule is every five minutes:

```cron
*/5 * * * * /opt/pm-edge/.venv/bin/python /opt/pm-edge/scripts/ops_status.py >> /opt/pm-edge/data/ops_status.log 2>&1
```

Serve the page with a simple HTTP server when browser access is needed:

```bash
cd /opt/pm-edge/data
python -m http.server 8080
```

Then open:

```text
http://<vps-ip>:8080/ops_status.html
```

For long-running browser access, run the HTTP server in `tmux` or add a small systemd unit. The companion status-page HTTP unit is intentionally not part of the current repo.

### Status Page Checks

Use the page as a quick operational triage tool:

- **Green service section:** service active, no restarts, memory below 80% of cap.
- **Yellow service section:** active with restarts or memory between 80% and 95% of cap.
- **Red service section:** inactive or memory above 95% of cap.

If the page is stale, check:

```bash
tail -100 /opt/pm-edge/data/ops_status.log
sudo systemctl status cron
```

If the page is current but capture rates are low, check:

```bash
journalctl -u forward-indexer.service --since "30 minutes ago"
```

## Laptop Sync

Set these environment variables on the laptop:

```bash
export PM_EDGE_VPS_HOST="pmedge@<vps-ip>"
export PM_EDGE_LOCAL_FORWARD_INDEX_DIR="$HOME/pm-edge-data/forward_index"
export PM_EDGE_LOCAL_RESOLVED_DIR="$HOME/pm-edge-data/resolved_market_outcomes"
```

Run a sync:

```bash
bash deploy/forward_indexer/rsync_to_laptop.sh
```

The script copies from:

```text
/opt/pm-edge/data/raw/forward_index/
/opt/pm-edge/data/raw/resolved_market_outcomes/
```

to:

```text
$PM_EDGE_LOCAL_FORWARD_INDEX_DIR
$PM_EDGE_LOCAL_RESOLVED_DIR
```

The script uses `rsync -avz --partial` and relies on rsync size/mtime checks to avoid re-copying unchanged parquet files while still repairing interrupted partial transfers.

When a local destination is under `/Volumes/`, the script first verifies that the external volume is actually mounted. If the drive is ejected, it exits `0` with an informational message and does not create `/Volumes/pm-edge-archive/` as a regular directory on the internal disk. This keeps cron quiet while preventing accidental internal-disk syncs.

Verify the local archive:

```bash
du -sh "$PM_EDGE_LOCAL_FORWARD_INDEX_DIR"
du -sh "$PM_EDGE_LOCAL_RESOLVED_DIR"
find "$PM_EDGE_LOCAL_FORWARD_INDEX_DIR" -maxdepth 2 -type d | sort
find "$PM_EDGE_LOCAL_RESOLVED_DIR" -maxdepth 2 -type d | sort
```

DuckDB smoke check:

```bash
.venv/bin/python - <<'PY'
import os
import duckdb

root = os.environ["PM_EDGE_LOCAL_FORWARD_INDEX_DIR"]
con = duckdb.connect()
con.sql(f"""
SELECT venue, COUNT(*) AS snapshots
FROM read_parquet('{root}/order_book_snapshots/**/*.parquet')
GROUP BY venue
ORDER BY venue
""").show()
PY
```

Recommended cadence while the data layer is proving out:

- Check VPS status page daily.
- Run rsync daily or after major collection windows.
- Run DuckDB smoke checks after each rsync until the archive process is boring.
- Keep raw parquet immutable; do not edit or rewrite synced parts by hand.

## Parquet Compaction

The indexer and resolution watcher write one small parquet part-file per partition on every flush (~every 15 s), so each `(table, venue, date)` directory accumulates thousands of tiny files over a week. That makes recursive `read_parquet('.../**/*.parquet')` globs hang, slows ext4 directory lookups, and slows rsync metadata sync. `scripts/compact_parquet.py` merges the small part-files in each partition into a few large ones.

Safety model:

- **Never touches today's partition.** Only partitions strictly older than today (UTC) are compacted, so the live writer is never raced.
- **Verify before delete.** The compacted output row count must equal the sum of the input row counts before any source file is removed.
- **Crash-safe.** Output is written to a hidden `.tmp-compact-*` file, renamed to its final `compact-*` name (the durable commit marker), and only then are the source `part-*` files deleted. A crash between the rename and the deletes is self-healed on the next run.
- **Idempotent.** A partition that already consists only of `compact-*` files (or a single file) is skipped, so it is safe to re-run.

Dry-run first (writes/deletes nothing, just logs what would happen):

```bash
/opt/pm-edge/.venv/bin/python /opt/pm-edge/scripts/compact_parquet.py --dry-run
```

Real run (compacts both configured archive roots — forward index and resolved outcomes):

```bash
/opt/pm-edge/.venv/bin/python /opt/pm-edge/scripts/compact_parquet.py
```

Useful flags: `--root PATH` (repeatable) to target specific roots, `--target-file-mb` to change the ~256 MiB per-file cap. Watch the `parquet_compaction_partition` / `parquet_compaction_summary` structured log lines for `files_before`/`files_after`/`rows`.

Install the cron entry from `deploy/forward_indexer/compact_parquet.cron`. Run `--dry-run` daily for a few days, then enable the real run at a low-activity hour **before** the laptop's morning rsync so the smaller file set is what gets pulled. This pairs with the journald retention cap on the VPS (`SystemMaxUse=500M`, `MaxRetentionSec=2week`): compaction reduces file count at the source, the journald cap is the log backstop.

## Notebook Setup

Install the analysis extras:

```bash
uv pip install -e '.[analysis]'
```

Point notebooks at the local archive:

```bash
export PM_EDGE_LOCAL_FORWARD_INDEX_DIR="$HOME/pm-edge-data/forward_index"
```

Start JupyterLab:

```bash
jupyter lab notebooks/
```

The first scaffold notebook is:

```text
notebooks/2026-05-22-first-look.ipynb
```

Notebook helper modules live in:

```text
notebooks/lib/queries.py
notebooks/lib/plots.py
```

The helpers create DuckDB views over the local archive and return Pandas DataFrames. `get_connection()` fails fast when the configured archive path is missing or contains no parquet files in the expected table directories. Missing individual tables still get empty schema-compatible views with warnings, which supports partially populated archives such as a capture with snapshots but no trades yet.

## Notebook Operating Rules

Use the conventions in `notebooks/README.md`:

- Name notebooks `YYYY-MM-DD-short-topic.ipynb`.
- Start with imports from `notebooks.lib.queries` and `notebooks.lib.plots`.
- Use `$PM_EDGE_LOCAL_FORWARD_INDEX_DIR`; do not hardcode archive paths.
- Keep DuckDB queries time-bounded with `timestamp_utc` filters.
- End every notebook with a `Findings` section.
- Update `notebooks/INDEX.md` after each notebook session.

The notebooks are for exploration, not strategy approval. Strategy conclusions require:

- enough clean forward data
- a separate execution simulator using captured book state
- per-market statistical accounting
- pre-registered Go / No-Go criteria

## Daily Operating Loop

1. Open the VPS status page.
2. Confirm service is active and heartbeat is fresh.
3. Check capture counts and gap detection.
4. Run laptop rsync.
5. Run the DuckDB smoke check locally.
6. If investigating data, open the current notebook and update `notebooks/INDEX.md`.
7. If a capture issue appears, inspect systemd journal before changing code.

## Weekly Operating Loop

1. Review storage growth and projected days until disk full.
2. Check whether Polymarket source mix remains mostly WebSocket.
3. Check Kalshi book quality for non-empty bid/ask levels.
4. Review reconnect and error counts.
5. Run one notebook pass focused on data quality, not edge discovery.
6. Record any persistent operational issue in docs or an issue tracker before implementing fixes.

## What Not To Do

- Do not use legacy `signals_*.parquet` backtests for strategy approval.
- Do not run notebooks on the VPS.
- Do not point notebook queries at `/opt/pm-edge` over SSHFS or ad hoc remote mounts.
- Do not introduce a web dashboard before the static HTML page proves insufficient.
- Do not change forward-indexer filters during an analysis window without recording the date and reason.
- Do not interpret row counts as independent market outcomes.
